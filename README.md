# Budget-aware харнесс на openJiuwen

Харнесс для соревнования openJiuwen Challenge 2026: за фиксированный бюджет токенов набрать
максимум баллов на 100 задачах. Главная идея: **всё, что можно сделать без модели, делает код
харнесса**. Он собирает контекст, отсеивает невыполнимое, исполняет и проверяет код.
Модель делает один короткий вызов на задачу и пишет только решающий фрагмент.

Результаты на сгенерированных наборах по 100 задач (около 20% невыполнимых), модель
`qwen3.8-27b-noreason`:

| набор | выполнимые решены | баллы | расход (out + in/10) | токены на невыполнимые |
| --- | --- | --- | --- | --- |
| 8 примеров организаторов | 8/8 | 20/20 | 650 | — |
| seed 4 | 80/81 | 265/269 | 7449 | 886 |
| seed 5 (в контейнере, команда регламента) | 73/73 | 215/215 | 5524 | 0 |

Единственная ошибка на seed 4 — артефакт генератора: в задаче получается отрицательный
остаток, а округление вниз для отрицательных чисел неоднозначно.

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

- Сборка занимает около 2 минут, образ весит 1.36 ГБ (`python:3.12.8-slim-bookworm` и openJiuwen 0.1.19).
- Все транзитивные версии зафиксированы в `requirements.lock`.
- При запуске ничего не скачивается. Ключей в репозитории нет: ключ приходит из `LLM_API_KEY`.

Аргументы `run_agent.py`:

| аргумент | по умолчанию | смысл |
| --- | --- | --- |
| `--tasks-dir` | `$TASKS` или `/data/tasks` | каталог задач |
| `--out` | `$OUT`, иначе `<tasks-dir>/answers.json` | JSON `{task_id: answer}`; если передан каталог, внутри создаётся `answers.json` |
| `--budget` | `$TOKEN_BUDGET`, иначе без лимита | бюджет в выходных токенах, если он известен заранее |
| `--workers` | 5 | параллельные сессии (не больше 5) |

После каждой решённой задачи харнесс сохраняет ответы атомарно (через временный файл и
`os.replace`) в трёх местах: `answer.txt` в каталоге задачи, `answer.txt` в её `workspace/`
и JSON с решениями. Задача, решённая до обрыва бюджета, не теряется.

### Неочевидные детали среды

- **`--read-only` и логи openJiuwen.** При первом импорте openJiuwen создаёт `./logs`
  относительно текущей папки. Под `--read-only --workdir /app` импорт падает с
  `Read-only file system: '/app/logs'`. Поэтому харнесс до импорта фреймворка переходит
  в `/tmp/agent`. Пути к задачам перед этим превращаются в абсолютные.
- Шумные INFO-логи openJiuwen (полный запрос и ответ на каждый вызов) понижены до WARNING.
- Код, который пишет модель, выполняется в каталоге задачи без переменных `LLM_*`:
  ключ ему недоступен.

## Как устроен харнесс

```
run_agent.py          планировщик: анализ -> приоритеты -> 5 воркеров -> сохранение
harness/tasks.py      загрузка задач, анализ без LLM: контекст, невыполнимость, оценка стоимости
harness/solvers.py    решатели по типам + универсальный текстовый ReAct-агент
harness/llm.py        вызовы через openjiuwen.core.foundation.llm.Model, учёт токенов, ретраи
harness/sandbox.py    исполнение кода модели с таймаутом
tools/gen_tasks.py    генератор тренировочного набора (с невыполнимыми и скрытыми тестами)
tools/grade.py        оценка прогона
traj/                 собранные траектории (каждый вызов LLM: промпт, ответ, токены)
```

LLM вызывается через `Model` из openJiuwen (провайдер OpenAI-совместимый, адрес берётся из
`LLM_BASE_URL`). Function calling не используется: по документации NeuralDeep у `-noreason`
моделей нет tools. Протокол текстовый: модель присылает блок ```` ```python ```` или
```` ```bash ````, харнесс его исполняет.

### Выбор модели

Замер на одном и том же арифметическом вопросе («ответь только числом»):

| модель | ответ | выходных токенов |
| --- | --- | --- |
| qwen3.8-27b-noreason | 116 (неверно) | 4 |
| qwen3.6-35b-a3b-noreason | 19 (неверно) | 3 |
| qwen3.8-27b (reasoning low) | 389 (верно) | 135 |
| qwen3.6-35b-a3b (reasoning не выключается) | 389 (верно) | 517 |

Вывод: считать модели не дают, они пишут код. Для кода хватает
`qwen3.8-27b-noreason`, и это самый дешёвый вариант. Рассуждающая `qwen3.8-27b` подключается
только третьей попыткой в кодинге, если две быстрые попытки не прошли тесты.

### Решатели (обычно один вызов на задачу)

| тип | что делает харнесс | что пишет модель | средний расход |
| --- | --- | --- | --- |
| math | вырезает служебные фразы из условия | короткую программу на python, которая печатает ответ | ~50 |
| data_analysis | сам читает CSV: колонки, 3 строки, диапазоны чисел, значения категорий; перед кодом модели подгружает `rows`/`tables` с уже приведёнными типами | одно выражение вида `print(sum(...))` | ~63 |
| search | индексирует KB по заголовкам, обходит связи `Ключ: Значение` (человек → работодатель → компания → …) на число шагов по вопросу; передаёт 1–8 нужных карточек | только значение ответа (`max_tokens=24`) | ~29 |
| coding | запускает тесты; если они уже проходят, сразу пишет DONE; передаёт исходник, тесты и вывод падений | только изменённые функции; харнесс вклеивает их по AST и перезапускает тесты | ~127 |
| прочее | список файлов | текстовый ReAct с bash, до 8 шагов, контекст подрезается | — |

Проверки в кодинге:

- файлы тестов хешируются и при любом изменении восстанавливаются;
- промпт требует чинить функции по смыслу имени, а не под видимые тесты: организаторы
  проверяют скрытыми тестами (в генераторе они тоже есть, `hidden/test_hidden.py`).

Ошибка исполнения уходит модели одной повторной попыткой. `ZeroDivisionError`, а в данных
`KeyError` или `FileNotFoundError` означают, что задача невыполнима, и повтор не делается.

### Распознавание невыполнимых задач

Первый слой работает без токенов, на этапе анализа:

- **search**: сущности из вопроса нет ни в заголовках, ни в тексте KB;
- **data**: нет упомянутого файла или колонки; значения в кавычках (`'gizmo-pro'`) нет ни
  в одной категориальной колонке; колонки из инструкции отсутствуют в файле;
- **math**: в условии деление «на 0 частей»; начальное количество не задано
  («unrecorded / unknown number»);
- **coding**: тесты противоречат друг другу. По AST один и тот же вызов `m.f(args)`
  проверяется на два разных литерала, или `m.f.__name__` сравнивается с другим именем.

Задачи с `p_feasible < 0.1` не запускаются. На ~600 сгенерированных задачах этот слой не дал
ни одного ложного срабатывания.

Второй слой — модель. Во всех промптах ей разрешено ответить `IMPOSSIBLE`, и харнесс тогда
не пишет ответ: неверный ответ баллов не даёт, так что писать его незачем.

### Оценка расхода и порядок решения

Стоимость задачи оценивается до запуска:
`est = (символы промпта / 3.3 / 10 + ожидаемый вывод[тип]) * ожидаемые попытки[тип]`.
Промпт харнесс строит сам, поэтому размер входа известен точно. Ожидаемый вывод и число
попыток взяты из траекторий (`traj/`). Пока идёт прогон, отношение фактической стоимости
к оценке по каждому типу сглаживается EMA, и оценка уточняется.

Приоритет: `reward * p_feasible * p_success[тип] / est`. Задачи решаются по убыванию
приоритета: при жёстком бюджете сначала берутся самые выгодные. Если бюджет известен
(`--budget`), задача с оценкой больше остатка пропускается, и воркер берёт следующую,
более дешёвую.

Учёт токенов ведётся по `usage` из ответа API: `completion_tokens`, где reasoning уже
учтён, плюс `prompt_tokens / 10`. Если прокси перестаёт отвечать (3 вызова подряд
отклонены или не прошли за 6 ретраев), харнесс прекращает брать новые задачи. Ответ 429
считается rate limit: харнесс ждёт и повторяет вызов.

## Траектории

Каждый вызов LLM пишется в JSONL (`$TRAJ_PATH`, по умолчанию `/tmp/trajectories.jsonl`):
тег задачи и попытки, модель, сообщения, ответ, входные и выходные токены, стоимость,
длительность. Итог прогона пишется в `$SUMMARY_PATH`. Примеры в `traj/`:

- `run_samples_trajectories.jsonl` — 8 задач организаторов;
- `run_seed4_trajectories.jsonl` и `run_seed4_summary.json` — 100 сгенерированных задач.

## Тренировочный набор

```bash
python tools/gen_tasks.py /tmp/train --n 100 --seed 1 --infeasible 0.2
python run_agent.py --tasks-dir /tmp/train
python tools/grade.py /tmp/train /tmp/run_summary.json
```

Генератор повторяет формат примеров организаторов и усложняет его:

- math: цепочки из 2–5 операций (отгрузка, поставки, деление с округлением, удвоение,
  списание процентов);
- data: 5 видов вопросов на 20–1000 строках;
- search: многошаговые вопросы до 4 переходов (ментор → работодатель → штаб-квартира);
- coding: 10 функций с типовыми багами плюс скрытые тесты.

Невыполнимые варианты: несуществующий человек или поле, отсутствующие товар, колонка или
файл, деление на 0, не заданное начальное количество, противоречивые тесты.
