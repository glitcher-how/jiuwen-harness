# Budget-aware харнесс на openJiuwen

Харнесс кодового агента на openJiuwen 0.1.19. Он получает каталог из 100 задач и решает их
в порядке выгодности, расходуя как можно меньше токенов.

Работа идёт в две фазы:

1. **Без модели.** Задачи, условие которых харнесс понимает полностью, решает код: 0 токенов.
2. **С моделью.** Всё остальное решает агент `ReActAgent` из openJiuwen. Харнесс сам
   собирает для него контекст, а инструмент агента исполняет и проверяет его код, поэтому
   на задачу обычно уходит один короткий вызов модели.

Невыполнимые задачи отсеиваются до обращения к модели.

## Сборка и запуск

Сборка из корня репозитория:

```bash
docker build -t hack:latest .
```

Запуск — командой из регламента, без изменений:

```bash
docker run --rm --name "run-${TEAM}" \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  hack:latest \
  /app/run_agent.py --tasks-dir /data/tasks
```

**Образ**
- Базовый образ: `python:3.12.8-slim-bookworm`.
- Все зависимости, включая транзитивные, зафиксированы в `requirements.lock`.
- Сборка занимает около 2 минут, размер образа 1.36 ГБ.
- При запуске ничего не скачивается. Ключей API в репозитории и образе нет: ключ берётся
  из `LLM_API_KEY`.

**Сеть.** Харнесс обращается только к `LLM_BASE_URL` по OpenAI-совместимому протоколу
(`POST {LLM_BASE_URL}/chat/completions`). Если адрес задан без `/v1` и прокси отвечает 404,
харнесс один раз пробует добавить `/v1`; если 404 повторяется, возвращает исходный адрес.

**Запуск под `--read-only`.** При импорте openJiuwen создаёт каталог `./logs` в текущей
папке, а `/app` доступна только на чтение. Поэтому харнесс до импорта фреймворка переходит
в `/tmp/agent`. Всё, что пишется во время работы, попадает в `/tmp` и в каталог задач.

### Входные и выходные данные

| что | где |
| --- | --- |
| задачи | `--tasks-dir` (по умолчанию `$TASKS`, иначе `/data/tasks`) |
| бюджет в выходных токенах | переменная окружения `BUDGET` (или аргумент `--budget N`) |
| ответ задачи | `answer.txt` рядом с `task.json`; копия в `workspace/` задачи |
| все ответы одним JSON | `--out` или `$OUT`, если путь доступен на запись; иначе `/tmp/answers.json` |
| траектории вызовов LLM | `/tmp/trajectories.jsonl` (`$TRAJ_PATH`) |
| итог прогона | `/tmp/run_summary.json` (`$SUMMARY_PATH`) |

- Ответы записываются сразу после решения каждой задачи. Запись атомарная: через временный
  файл и `os.replace`. Задачи, решённые до исчерпания бюджета или таймаута, сохраняются.
- Пишется только ответ, без пояснений. Для задач на исправление кода — `DONE`, и только
  если все тесты проходят.
- Ответ приводится к виду, который ждёт проверка из поля `check`: для `exact_int` — целое
  без разделителей и единиц (`1,735` → `1735`, `389 boxes` → `389`); в поиске — написание
  значения как в базе знаний. Поле `expected` харнесс не читает.
- Для задачи, признанной невыполнимой, `answer.txt` не создаётся.
- Файлы тестов не меняются: харнесс сверяет их хеши и при расхождении восстанавливает.
- Без `BUDGET` харнесс работает, пока прокси отвечает. `--workers` задаёт число
  параллельных сессий, от 1 до 5, по умолчанию 5.
- Неизвестные аргументы командной строки игнорируются и не ломают запуск.
- Время работы ограничено 55 минутами: после этого новые задачи не начинаются.

## Устройство

```
run_agent.py              планировщик: анализ -> фаза без модели -> приоритеты -> до 5 воркеров
harness/tasks.py          анализ без LLM: контекст, признаки невыполнимости, оценка стоимости
harness/deterministic.py  решатели без модели
harness/llm.py            агенты openJiuwen (ReActAgent), их инструменты, учёт токенов, ретраи
harness/solvers.py        решатели по типам задач: какой агент, с каким контекстом и инструментом
harness/sandbox.py        исполнение кода с таймаутом, без переменных LLM_* в окружении
traj/                     собранные траектории
tools/                    генераторы тренировочных задач, оценка прогона, сравнение моделей,
                          проверка решателей без модели (в образ не входят)
```

### Агент на openJiuwen

Каждое обращение к модели делает `ReActAgent` из openJiuwen (`harness/llm.py`):

- **Модель агента** — `MeteredModel`, наследник `openjiuwen...llm.Model`. Он считает расход
  каждого вызова (`выход + вход/10`), повторяет запрос при ограничении частоты и
  останавливает работу, когда бюджет исчерпан.
- **Инструменты** — три `LocalFunction` openJiuwen, зарегистрированные в его менеджере
  ресурсов:
  - `run_python` — выполнить программу в каталоге задачи;
  - `apply_fix` — вклеить исправленные функции в модуль и запустить тесты;
  - `bash` — выполнить команду.
- **Сессия.** У агента свой системный промпт под тип задачи; контекст диалога ведёт
  openJiuwen. Повторная попытка — короткое продолжение той же сессии.
- **Число шагов.** Контекст готовит харнесс, поэтому агенту математики, данных, поиска и
  кодинга хватает одного вызова модели (`max_iterations=1`). Агент для задач
  неизвестного типа работает полным циклом ReAct с `bash` до 8 шагов.

**Как модель передаёт код инструменту.** По умолчанию — блоком ```` ```python ````, который
харнесс отдаёт тому же инструменту openJiuwen. Нативный вызов инструмента включается
переменной `AGENT_TOOLS=1` и даёт ту же точность, но с каждым запросом уходит схема
инструмента и служебная преамбула модели. На 40 независимых задачах это 8571 токен против
5269, то есть +63%, поэтому по умолчанию он выключен. Многошаговый агент всегда использует
нативные вызовы.

### Фаза 1: решение без модели

Код берётся за задачу, только если понимает её целиком. При любом сомнении он не отвечает,
и задача уходит модели.

| тип | когда код отвечает сам |
| --- | --- |
| math | каждое предложение условия совпало с известным шагом (отгрузка, поставки, деление на склады с округлением вниз, удвоение); одно незнакомое предложение — и задача идёт модели |
| data_analysis | вопрос совпал с известным агрегатом («сколько единиц товара X продано в месяцах A–B»), все нужные колонки есть, все значения разобраны как числа |
| search | вопрос разобран в цепочку переходов по карточкам (человек → работодатель → штаб-квартира, ментор и т. п.), и каждая карточка и каждое поле найдены однозначно |
| coding | исправление найдено перебором одиночных правок упавшей функции (см. ниже) |

**Починка кода без модели.** Для каждого упавшего теста харнесс определяет по AST, какую
функцию он вызывает, и перебирает её одиночные правки: знак сравнения, арифметическая
операция, константа ±1, `sorted`/`reversed`, `min`/`max`, отрицание условия. Кандидат
принимается, только если его тесты проходят и ни один другой тест не ломается.

Одного прохождения тестов мало: правка может подогнать функцию под единственный пример.
Поэтому, когда тесты проходят несколько кандидатов, харнесс запускает их на дополнительных
входах, построенных из аргументов тестов, и сравнивает поведение. Настоящее исправление
обычно представлено несколькими равносильными записями (`>` и `>=`, `== 0` и `!= 1`), а
подгонка стоит особняком (`x % 3 == 1` для счёта чётных). Принимается только кандидат из
явного большинства; иначе задача идёт модели. Если кодом удалось исправить часть функций,
эти исправления остаются, а модель получает задачу поменьше.

Проверка на 508 задачах с известными ответами и скрытыми тестами
(`python tools/check_det.py`): неверных ответов кода — 0.

### Фаза 2: решение с моделью

| тип | что делает харнесс | что пишет модель |
| --- | --- | --- |
| math | убирает служебные фразы из условия; сравнивает два независимых решения (см. ниже) | короткую программу, которая печатает ответ |
| data_analysis | сам читает таблицу (разделитель определяется по заголовку) и передаёт сводку: колонки, первые строки, диапазоны чисел, значения категорий, число пустых ячеек; перед кодом модели загружает таблицы в `rows`/`tables` с приведёнными типами | одно-две строки вида `print(sum(...))` |
| search | индексирует базу знаний по заголовкам, обходит ссылки между карточками и передаёт только связанные с вопросом | только значение ответа |
| coding | запускает тесты и передаёт только упавшие тесты, функции, которые они вызывают, и по одной строке ошибки на тест; если не каждая функция файла покрыта тестом, передаёт файл целиком; затем отдаёт весь модуль на проверку (см. ниже) | только изменённые функции; инструмент вклеивает их по AST и перезапускает тесты |
| другое | передаёт список файлов | команды `bash` в цикле ReAct, до 8 шагов |

Если исполнение кода модели завершилось ошибкой, она возвращается модели, и та делает одну
повторную попытку. В кодинге после двух неудач подключается рассуждающая `qwen3.8-27b` —
но только если правки хоть как-то изменили картину падений. Если тесты падают точно так же,
причина не в этом файле, и дорогая модель не вызывается.

### Выбор модели

Все модели стоят одинаково за токен, поэтому модель выбирается по точности и длине ответа.
Сравнение `-noreason` моделей на 400 выполнимых задачах (по 100 на тип), только через
модель, без фазы 1. Стоимость — средняя на задачу в единицах «выход + вход/10».

| тип | qwen3.8-27b-noreason: точность / стоимость | qwen3.6-35b-a3b-noreason: точность / стоимость |
| --- | --- | --- |
| coding | 100% / 139 | 100% / 215 |
| data_analysis | 100% / 65 | 100% / 67 |
| math | 100% / 67 | 91% / 66 |
| search | 100% / 24.5 | 100% / 24.5 |

Итоговый выбор:

- `qwen3.8-27b-noreason` — данные, кодинг и первые два решения в математике.
- `qwen3.8-27b` с `reasoning_effort=low` — поиск, который не распознала фаза 1, арбитр в
  математике и третья попытка в кодинге. В поиске модель без рассуждений выбирает не ту
  карточку, когда нужно отфильтровать или сравнить записи, и угадывает, когда база не
  даёт ответа.

### Математика: два дешёвых решения вместо одного дорогого

Сюда попадают только формулировки, которые не распознала фаза 1. Замер на 71 такой задаче:

| способ | верно | токенов на задачу |
| --- | --- | --- |
| модель без рассуждений, обычный промпт | 68/71 | 68 |
| модель без рассуждений, промпт «одно присваивание на предложение» | 70/71 | 70 |
| рассуждающая модель | 70/71 | 286 |
| два дешёвых решения; при расхождении — рассуждающая модель | 71/71 | 161 |

Каждый решатель по отдельности теряет или неверно читает шаг в 1–4% задач, включая
рассуждающую модель. Но ошибаются они по-разному, поэтому совпадение двух по-разному
настроенных дешёвых решений работает как бесплатная проверка. Харнесс принимает ответ,
если оба совпали, и зовёт рассуждающую модель, только если они разошлись.

### Кодинг: проверка на ошибки, которых не видят тесты

Проверяющие запускают свой, более полный файл тестов. Поэтому после того, как видимые тесты
прошли, ещё один агент просматривает весь модуль: имя функции, докстринг и текст задачи
задают её поведение в общем виде, а тест показывает только один пример. Предложенная
правка принимается, только если видимые тесты по-прежнему проходят; иначе файл остаётся
прежним.

Замер на 40 задачах со вторым багом, который видимый тест не ловит (`tools/gen_latent.py`),
и на тех же 40 задачах без него:

| вариант | найдено скрытых багов | сломано в чистых задачах | токенов на задачу |
| --- | --- | --- | --- |
| без проверки | 0/40 | — | 0 |
| проверка моделью без рассуждений | 36/40 | 0/40 | ~80 |
| проверка рассуждающей моделью | 39/40 | 0/40 | 540–1070 |

По умолчанию проверяет модель без рассуждений. Рассуждающая модель подключается только в
режиме повышенной надёжности.

### Режим повышенной надёжности

Если задач не больше десяти, а бюджета на задачу не меньше 5000 токенов, харнесс считает,
что цена ошибки выше цены токенов. Так выглядит отборочный прогон из двух выполнимых задач,
где одна ошибка снимает команду. В этом режиме:

- каждый ответ подтверждается независимыми решениями, пока два из них не совпадут
  (разные промпты, разные модели, для поиска — разный объём базы знаний);
- ни одна задача не пропускается и не откладывается как невыполнимая;
- модуль в кодинге дополнительно проверяет рассуждающая модель.

Режим выбирается автоматически; переменная `ASSURE=1` включает его принудительно,
`ASSURE=0` выключает.

## Оценка расхода и порядок решения

**Учёт.** Расход считается по полю `usage` каждого ответа:
`completion_tokens + prompt_tokens / 10`. Токены рассуждений входят в `completion_tokens`.
Расход ведётся общий и отдельно по каждой задаче и сверяется с `BUDGET`.

**Оценка до запуска.** Промпт строит сам харнесс, поэтому длина входа известна заранее:

```
est = (символы промпта / 3.3 / 10 + ожидаемый вывод[тип]) * ожидаемое число попыток[тип]
```

Ожидаемый вывод и число попыток по типам взяты из собранных траекторий. Во время прогона
отношение фактического расхода к оценке по каждому типу сглаживается экспоненциальным
средним, и последующие оценки поправляются.

**Порядок.** Сначала идёт фаза 1: она бесплатна. Оставшиеся задачи сортируются по
`reward * p_feasible * p_success[тип] / est` и решаются по убыванию. Задача, чья оценка
больше остатка бюджета, пропускается, и берётся следующая, более дешёвая.

Проверка при `BUDGET=1500` на 100 задачах: 42 задачи решены без модели, затем модель взяла
18 задач со средней отдачей 2.6 балла на 100 токенов оценки; у 30 оставшихся — 1.1.
Расход остановился на 1511.

**Остановка.** Ответ 429 считается ограничением частоты: харнесс ждёт и повторяет запрос.
Если три вызова подряд отклонены или остались без ответа после 6 попыток, прокси считается
исчерпанным, и новые задачи не начинаются.

## Поиск невыполнимых задач

Неверный ответ баллов не даёт, поэтому на невыполнимую задачу не стоит тратить токены.

**1. Без LLM, на этапе анализа.** Признаки делятся на точные и эвристические.

Точные доказывают, что задачу решить нельзя. Такие задачи не запускаются:

| тип | признак |
| --- | --- |
| coding | один и тот же вызов чистой функции с одинаковыми литералами должен вернуть два разных значения; нет исходников |
| data_analysis | упомянутого файла нет нигде в каталоге задачи; файл пуст |
| search | база знаний пуста или отсутствует |
| math | деление «на 0 частей» |

«Чистая» функция — та, что читает только свои аргументы, локальные переменные и встроенные
имена. Методы объектов сюда не относятся: два вызова `stack.pop()` подряд законно дают
разные результаты.

Эвристические признаки зависят от формулировки и могут ошибиться:

| тип | признак |
| --- | --- |
| search | сущности из вопроса нет ни в заголовках, ни в тексте базы знаний |
| data_analysis | значения в кавычках нет ни в одной категориальной колонке; названной колонки нет в файле |
| math | начальное количество не задано |
| coding | противоречие в тестах, которое не доказано; тест читает файл данных, которого нет в задаче |

Задачи с эвристическим признаком не пропускаются. Они идут в конец очереди и получают одну
короткую попытку: без повторов, без рассуждающей модели и не больше 200 выходных токенов.
Если эвристика ошиблась на выполнимой задаче, балл за неё не теряется.

**2. Модель.** Во всех промптах модели разрешено ответить `IMPOSSIBLE`; деление на ноль при
исполнении математической программы означает то же самое. Ответ тогда не записывается.

## Траектории

Каждый вызов LLM записывается одной строкой JSONL: тег задачи и номер попытки, модель,
отправленные сообщения, ответ и вызовы инструментов, входные и выходные токены, стоимость, длительность,
`finish_reason`. Итог прогона по задачам — статус, ответ, фактический и оценённый расход,
причина отсева, решена ли без модели — сохраняется отдельно.

| файлы в `traj/` | набор | результат |
| --- | --- | --- |
| — | 8 примеров организаторов | 8/8, расход 0: все решены без модели, вызовов LLM нет |
| `generated100_*` | 100 задач в формате примеров, из них 17 невыполнимых | 83/83 выполнимых, расход 7399; 42 решены без модели |
| `variants120_*` | 120 задач с другими формулировками, именами файлов и полей, классами вместо функций | 120/120, расход 14083; 6 решены без модели |

Набор `variants120` нужен, чтобы проверить путь через модель: формулировки в нём нарочно
не совпадают с шаблонами фазы 1.

## Тренировочные наборы

- `tools/gen_tasks.py` — задачи в формате примеров организаторов, с ответами и скрытыми
  тестами. Около 20% невыполнимы: несуществующий человек или поле, отсутствующие товар,
  колонка или файл, деление на 0, не заданное начальное количество, противоречивые тесты.
- `tools/gen_latent.py` — кодинг с ловушкой: второй баг, который видимый тест не ловит,
  и более строгие скрытые тесты; с ключом `--clean` — те же задачи без ловушки.
- `tools/gen_variants.py` — те же четыре типа в другом оформлении: перефразированные
  вопросы, CSV с разделителем `;`, база знаний с другими полями и вложенными папками,
  классы и импорт `from ... import`.

python tools/grade.py /tmp/train /tmp/run_summary.json
