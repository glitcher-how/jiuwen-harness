# Budget-aware харнесс на openJiuwen

Харнесс кодового агента на openJiuwen 0.1.19. Он получает каталог из 100 задач и решает их
в порядке выгодности, расходуя как можно меньше токенов.

Принцип: всё, что можно сделать без модели, делает код харнесса. Харнесс сам:
- собирает контекст;
- отсеивает невыполнимые задачи;
- исполняет код модели и проверяет результат.

Модель обычно делает один короткий вызов на задачу и пишет только решающий фрагмент.

## Сборка и запуск

Сборка из корня репозитория:

```bash
docker build -t hack:latest .
```

Запуск — командой из регламента, без изменений:

```bash
docker run --rm --name "run-${TEAM}" \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  hack:latest \
  /app/run_agent.py --tasks-dir /data/tasks
```

**Образ**
- Базовый образ: `python:3.12.8-slim-bookworm`.
- Все зависимости, включая транзитивные, зафиксированы в `requirements.lock`.
- Сборка занимает около 2 минут, размер образа 1.36 ГБ.
- При запуске ничего не скачивается. Ключей API в репозитории и образе нет: ключ берётся
  из `LLM_API_KEY`.

**Сеть.** Харнесс обращается только к `LLM_BASE_URL` по OpenAI-совместимому протоколу
(`POST {LLM_BASE_URL}/chat/completions`). Если адрес задан без `/v1` и прокси отвечает 404,
харнесс один раз пробует добавить `/v1`; если 404 повторяется, возвращает исходный адрес.

**Запуск под `--read-only`.** При импорте openJiuwen создаёт каталог `./logs` в текущей
папке, а `/app` доступна только на чтение. Поэтому харнесс до импорта фреймворка переходит
в `/tmp/agent`. Всё, что пишется во время работы, попадает в `/tmp` и в каталог задач.

### Входные и выходные данные

| что | где |
| --- | --- |
| задачи | `--tasks-dir` (по умолчанию `$TASKS`, иначе `/data/tasks`) |
| ответ задачи | `answer.txt` в каталоге задачи, копия в её `workspace/` |
| все ответы одним JSON | `--out` или `$OUT`, если путь доступен на запись; иначе `/tmp/answers.json` |
| траектории вызовов LLM | `/tmp/trajectories.jsonl` (`$TRAJ_PATH`) |
| итог прогона | `/tmp/run_summary.json` (`$SUMMARY_PATH`) |

- Ответы записываются сразу после решения каждой задачи. Запись атомарная: через временный
  файл и `os.replace`. Задачи, решённые до исчерпания бюджета или таймаута, сохраняются.
- Пишется только ответ, без пояснений. Для задач на исправление кода — `DONE`, и только
  если все тесты проходят.
- Файлы тестов не меняются: харнесс сверяет их хеши и при расхождении восстанавливает.
- Необязательные параметры:
  - `--budget N` или `$TOKEN_BUDGET` — бюджет в выходных токенах, если он известен заранее;
  - `--workers` — число параллельных сессий, от 1 до 5, по умолчанию 5.
- Неизвестные аргументы командной строки игнорируются и не ломают запуск.
- Время работы ограничено 55 минутами: после этого новые задачи не начинаются.

## Устройство

```
run_agent.py          планировщик: анализ задач -> приоритеты -> до 5 воркеров -> сохранение
harness/tasks.py      анализ без LLM: контекст, признаки невыполнимости, оценка стоимости
harness/solvers.py    решатели по типам задач и универсальный текстовый ReAct-агент
harness/llm.py        вызовы через openjiuwen.core.foundation.llm.Model, учёт токенов, ретраи
harness/sandbox.py    исполнение кода модели с таймаутом, без переменных LLM_* в окружении
traj/                 собранные траектории
tools/                генератор тренировочных задач, оценка прогона, сравнение моделей
                      (в образ не входят)
```

Модель вызывается через класс `Model` из openJiuwen. Function calling не используется:
у `-noreason` моделей нет tools, поэтому протокол текстовый. Модель присылает блок
```` ```python ```` или ```` ```bash ````, харнесс его исполняет и возвращает результат.

### Решатели

| тип | что делает харнесс | что пишет модель |
| --- | --- | --- |
| math | убирает служебные фразы из условия | короткую программу, которая печатает ответ |
| data_analysis | сам читает CSV и передаёт сводку: колонки, первые строки, диапазоны чисел, значения категорий; перед кодом модели загружает таблицы в `rows`/`tables` с приведёнными типами | одно-две строки вида `print(sum(...))` |
| search | индексирует базу знаний по заголовкам и обходит связи `Ключ: Значение` (человек → работодатель → компания) ровно на столько шагов, сколько требует вопрос; если модель отвечает IMPOSSIBLE, повторяет с двумя дополнительными шагами | только значение ответа (`max_tokens=24`) |
| coding | запускает тесты (если они уже проходят — сразу `DONE`) и передаёт исходник, тесты и вывод падений | только изменённые функции; харнесс вклеивает их по AST и перезапускает тесты |
| другое | передаёт список файлов | ReAct с bash: до 8 шагов, история подрезается |

Защиты от типичных ошибок модели:
- **Счёт в уме.** Программа из одного `print(число)` в математике отклоняется, и модель
  получает просьбу записать шаги кодом. Без кода модели без рассуждений ошибаются в
  арифметике.
- **Подгонка под видимые тесты.** Решения проверяются скрытыми тестами, поэтому промпт
  требует чинить функции по смыслу их имени, а не под конкретные проверки.
- **Неудачное исполнение.** Ошибка возвращается модели, и она делает одну повторную попытку.
  В кодинге после двух неудач подключается рассуждающая `qwen3.8-27b`
  (`reasoning_effort=low`).

### Выбор модели

Все модели стоят одинаково за токен. Поэтому модель выбирается по точности и длине ответа.
Ниже — сравнение на 400 выполнимых задачах тренировочного набора (по 100 на тип), без
подключения рассуждающей модели. Стоимость — средняя на задачу в единицах
«выход + вход/10».

| тип | qwen3.8-27b-noreason: точность / стоимость | qwen3.6-35b-a3b-noreason: точность / стоимость |
| --- | --- | --- |
| coding | 100% / 139 | 100% / 215 |
| data_analysis | 100% / 65 | 100% / 67 |
| math | 100% / 67 | 91% / 66 |
| search | 100% / 24.5 | 100% / 24.5 |

Для всех типов используется `qwen3.8-27b-noreason`. Рассуждающие модели верно считают и без
кода, но тратят на тот же вопрос в 30–100 раз больше выходных токенов (135 у `qwen3.8-27b`
и 517 у `qwen3.6-35b-a3b` против 4 у `-noreason`).

## Оценка расхода и порядок решения

**Учёт.** Расход считается по полю `usage` каждого ответа:
`completion_tokens + prompt_tokens / 10`. Токены рассуждений входят в `completion_tokens`.
Расход ведётся общий и отдельно по каждой задаче.

**Оценка до запуска.** Промпт строит сам харнесс, поэтому длина входа известна заранее:

```
est = (символы промпта / 3.3 / 10 + ожидаемый вывод[тип]) * ожидаемое число попыток[тип]
```

Ожидаемый вывод и число попыток по типам взяты из собранных траекторий. Во время прогона
отношение фактического расхода к оценке по каждому типу сглаживается экспоненциальным
средним, и последующие оценки поправляются.

**Порядок.** Приоритет задачи — `reward * p_feasible * p_success[тип] / est`; задачи
решаются по убыванию приоритета. Если бюджет известен, задача, чья оценка больше остатка,
пропускается, и берётся следующая, более дешёвая.

**Остановка.** Ответ 429 считается ограничением частоты: харнесс ждёт и повторяет запрос.
Если три вызова подряд отклонены или остались без ответа после 6 попыток, прокси считается
исчерпанным, и новые задачи не начинаются.

## Поиск невыполнимых задач

Неверный ответ баллов не даёт, поэтому на невыполнимую задачу не стоит тратить токены.
Проверка идёт в два слоя.

**1. Без LLM, на этапе анализа.** Задаче выставляется `p_feasible`:

| тип | признак |
| --- | --- |
| search | сущности из вопроса нет ни в заголовках, ни в тексте базы знаний |
| data_analysis | нет упомянутого файла или колонки; значения в кавычках нет ни в одной категориальной колонке; колонок из инструкции нет в файле |
| math | деление «на 0 частей»; начальное количество не задано |
| coding | тесты противоречат друг другу: по AST один и тот же вызов проверяется на два разных литерала, или `f.__name__` сравнивается с другим именем |

Задачи с `p_feasible < 0.1` не запускаются. Остальные признаки снижают приоритет.

**2. Модель.** Во всех промптах модели разрешено ответить `IMPOSSIBLE`. Кроме того,
`ZeroDivisionError`, а в задачах по данным `KeyError` и `FileNotFoundError` при исполнении
означают, что задача невыполнима. В обоих случаях ответ не записывается.

## Траектории

Каждый вызов LLM записывается одной строкой JSONL:
- тег задачи и номер попытки;
- модель, отправленные сообщения и ответ;
- входные и выходные токены, стоимость, длительность, `finish_reason`.

Итог прогона по задачам — статус, ответ, фактический и оценённый расход, причина отсева —
сохраняется отдельно. В `traj/` лежат траектории текущей версии:

| файл | набор | результат |
| --- | --- | --- |
| `samples_trajectories.jsonl` | 8 примеров организаторов | 8/8, расход 553 |
| `generated100_trajectories.jsonl`, `generated100_summary.json` | 100 задач тренировочного набора, из них 24 невыполнимые | 76/76 выполнимых, расход 6182, на невыполнимые 257 |

## Тренировочный набор

Генератор `tools/gen_tasks.py` создаёт задачи в формате примеров организаторов, с ответами
и скрытыми тестами для проверки:
- math: цепочки из 2–5 операций;
- data_analysis: 5 видов вопросов на таблицах от 20 до 1000 строк;
- search: вопросы до 4 переходов по базе знаний;
- coding: 10 функций с типовыми ошибками.

Около 20% задач невыполнимы: несуществующий человек или поле, отсутствующие товар, колонка
или файл, деление на 0, не заданное начальное количество, противоречивые тесты.

```bash
python tools/gen_tasks.py /tmp/train --n 100 --seed 1
python run_agent.py --tasks-dir /tmp/train
python tools/grade.py /tmp/train /tmp/run_summary.json
python tools/bench.py /tmp/train /tmp/bench qwen3.8-27b-noreason qwen3.6-35b-a3b-noreason
```
